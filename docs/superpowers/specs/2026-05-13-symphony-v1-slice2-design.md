# Symphony v1.0 — Slice 2: Codex App-Server End-to-End

**Date:** 2026-05-13
**Status:** Approved (design); pending implementation plan
**Scope:** Slice 2 of phase 1. Builds on slice 1 (`v1-slice1`, PR #1). Lands on a new branch `v1-slice2` off `main` once slice 1 merges.

## Goal

Replace `codex_stub` with a real Codex `app-server` v2 JSON-RPC client end-to-end. Reuse every cross-cutting piece slice 1 built — `Policy`, `OrchestratorEventBus`, `ApprovalRouter`, `mcp_bridge`, `vcs::{push_branch, open_pr}`, the SSE endpoint, the dashboard approval toast — so the slice-2 diff is contained to a new `codex-client` crate plus a thin harness adapter.

## Non-Goals

- Long-running multi-turn sessions (single turn per claim).
- `thread/resume`, `thread/fork`, archival.
- Concurrent turns from one `Client` instance.
- Codex's realtime audio/SDP/transcript channels.
- v1 protocol coverage beyond `Initialize` (handshake only).
- Metric framework wiring (log-only observability for now).

## Architecture

Three sequential commit stages on `v1-slice2`. Each builds, tests, and lands independently.

- **Stage 1 — Types.** New crate `crates/codex-client`. `build.rs` runs `typify` over `docs/codex-protocol/codex_app_server_protocol.v2.schemas.json` to generate `protocol::v2::*`. Hand-roll `protocol::v1::Initialize{Params,Response}` (handshake only). Hand-roll the four method-dispatch enums — `ClientRequest`, `ClientNotification`, `ServerNotification`, plus a thin `JsonRpcMessage` envelope — that pattern-match on `method` strings and wrap the typify-generated param structs.
- **Stage 2 — Transport + correlation.** `transport::StdioTransport` (newline-delimited JSON over child stdio, mockable via `tokio::io::DuplexStream`). `dispatcher::Dispatcher` owns the read loop and demultiplexes responses (oneshot by id) and notifications (channel). Public surface: `Client::connect(child) -> (Client, NotificationStream)`.
- **Stage 3 — Client API + harness.** `Client::{initialize, start_turn, interrupt, thread_approve_guardian_denied_action}`. New `harness::codex::CodexHarness` in `symphony-core` that spawns `codex app-server --listen stdio` with `-c mcp_servers.linear=...`, calls `initialize`, drives `turn/start` with `permissions` from `Policy`, pumps notifications into `AgentEvent`/`OrchestratorEvent::ToolCall`, routes guardian-denied actions through `ApprovalRouter`, sends overrides via `thread/approveGuardianDeniedAction`. Replaces `codex_stub`.

### Reused unchanged from slice 1

`OrchestratorEventBus`, `ApprovalRouter`, `Policy`, `HarnessContext`, `mcp_bridge::generate_mcp_config_json`, `vcs::{push_branch, open_pr}`, captured-policy flow on claim, SSE `/api/v1/events` endpoint, `POST /api/v1/approvals/{id}`, dashboard approval toast.

### Approval flow correction (v2 schema review)

The slice-1 spec assumed v1's request-driven approval shape (four `ServerRequest` approval types). v2 inverts this: approvals are *notification-driven*. There is no `ServerRequest` enum in v2.

Codex's internal **guardian** assesses each action (command exec, apply patch, network access, MCP tool call, permission elevation) against the `permissions` profile we pass on `turn/start`, then emits `ItemGuardianApprovalReviewStartedNotification → CompletedNotification` with status `approved`/`denied`/`timedOut`/`aborted`. The client overrides a denied action via `ClientRequest: thread/approveGuardianDeniedAction`.

This makes the `permissions` argument on `turn/start` the **primary** policy gate — load-bearing in a way it isn't on Claude — and reframes the operator dashboard prompt as an **override path** for guardian denials, not a per-tool-call gate.

## Components

### `crates/codex-client` (new crate, ~1.2k LOC total)

Standalone workspace member. Single dependency consumer is `symphony-core::harness::codex`.

#### `protocol::v1` (~80 LOC, hand-rolled)

`InitializeParams` / `InitializeResponse` only. Hand-rolled because (a) it's two structs and (b) v1 and v2 must remain type-distinct so they can never be confused in code.

#### `protocol::v2` (~600 LOC, generated by `build.rs`)

`typify` reads `docs/codex-protocol/codex_app_server_protocol.v2.schemas.json` at build time, emits `v2.rs` into `OUT_DIR`. **Hard fail** if the schema file is missing — the schema is committed to the repo, so this only fires on intentional deletion.

#### `protocol::messages` (~120 LOC, hand-rolled dispatch)

Three enums dispatching on JSON-RPC `method`:

```rust
#[serde(tag = "method", content = "params")]
pub enum ClientRequest { Initialize(v1::InitializeParams), TurnStart(v2::TurnStartParams), TurnInterrupt(v2::TurnInterruptParams), ThreadApproveGuardianDeniedAction(v2::ThreadApproveGuardianDeniedActionParams), /* extend as needed */ }
#[serde(tag = "method", content = "params")]
pub enum ClientNotification { /* none used in slice 2 */ }
#[serde(tag = "method", content = "params")]
pub enum ServerNotification { /* ~15 variants we handle, see §Data Flow; everything else falls into Unknown(serde_json::Value) */ }
```

Method-name strings live only here; downstream code matches the enum.

#### `transport::StdioTransport` (~150 LOC)

Owns `ChildStdin` (write half) and `BufReader<ChildStdout>` (read half). `send(JsonRpcMessage)` serializes + writes a newline-delimited JSON frame. `recv() -> JsonRpcMessage` reads one line, parses. No correlation logic — that lives in the dispatcher. Mockable via `tokio::io::DuplexStream`.

#### `dispatcher::Dispatcher` (~250 LOC)

Owns the read-loop task. Demultiplexes:
- Responses (has `id`, no `method`) → matching `oneshot::Sender<ClientResult<Value>>` from a `HashMap<RequestId, _>`.
- Notifications (no `id`, has `method`) → `mpsc::Sender<ServerNotification>`.

On transport EOF or parse-fatal error: drains the waiter map (every pending oneshot resolves `Err(TransportClosed)`), closes the notification channel, exits. `JoinHandle` aborted on `Drop`.

Panic safety: read loop wraps step-handling in `std::panic::catch_unwind`. A panic logs at `error` and closes channels (callers see `TransportClosed` — no silent hangs).

#### `Client` (~200 LOC)

```rust
pub struct Client { /* write half + dispatcher handle */ }

impl Client {
    pub async fn connect(child: tokio::process::Child) -> ClientResult<(Client, NotificationStream)>;
    pub async fn initialize(&self, params: v1::InitializeParams) -> ClientResult<v1::InitializeResponse>;
    pub async fn start_turn(&self, params: v2::TurnStartParams) -> ClientResult<v2::TurnStartResponse>;
    pub async fn interrupt(&self, turn_id: v2::TurnId) -> ClientResult<()>;
    pub async fn thread_approve_guardian_denied_action(&self, params: v2::ThreadApproveGuardianDeniedActionParams) -> ClientResult<v2::ThreadApproveGuardianDeniedActionResponse>;
}

impl Drop for Client {
    fn drop(&mut self) {
        // Drop is sync. Spawn a fire-and-forget task on the current runtime to
        // write `turn/interrupt` (capped 500ms via tokio::time::timeout). Then
        // `child.start_kill()` synchronously.
    }
}
```

Each typed method: take typed params, generate `RequestId`, register oneshot in dispatcher's waiter map, serialize + write request, await oneshot.

#### Error type

```rust
#[derive(Debug, thiserror::Error)]
pub enum ClientError {
    #[error("transport closed")]                       TransportClosed,
    #[error("io: {0}")]                                 Io(#[from] std::io::Error),
    #[error("invalid json on {role}: {source}")]        Decode { role: &'static str, source: serde_json::Error },
    #[error("server error {code}: {message}")]          JsonRpc { code: i64, message: String },
    #[error("request {0} dropped before response")]    OneshotDropped(RequestId),
    #[error("server sent unknown method: {0}")]        UnknownMethod(String),
}
```

### `symphony-core::harness::codex` (~350 LOC, replaces `codex_stub.rs`)

`CodexHarness` implementing `Harness::run`. Mirrors `claude_code.rs` so reviewers can diff:

1. **Spawn.** `codex app-server --listen stdio` with `-c mcp_servers.linear=<mcp_bridge::generate_mcp_config_json(...)>`. Env vars `SYMPHONY_LINEAR_TOKEN`, `SYMPHONY_LINEAR_ENDPOINT`, `SYMPHONY_ISSUE_ID` carry forward to the bridge.
2. **Connect + initialize.** `Client::connect(child)` → `client.initialize(InitializeParams { protocol_version, client_info, capabilities })`.
3. **Turn.** `client.start_turn(TurnStartParams { thread_id: None, prompt: ctx.prompt, permissions: translate_codex_permissions(&ctx.policy), ... })`. On success, emit `AgentEvent::TurnStarted`.
4. **Event pump.** `tokio::select!` loop over `NotificationStream`, dispatching per §Data Flow. Maintains `pending_reviews: HashMap<ReviewId, GuardianApprovalReviewAction>`.
5. **Termination.** Exits on `turn/completed` or transport closure. Returns `HarnessOutcome { thread_id, turn_id, success, error }`.
6. **Cleanup.** `Drop` on `Client` interrupts then kills the child.

`select_harness` in `harness/mod.rs`: route `"codex" | "codex-app-server"` to `CodexHarness`. Delete `harness/codex_stub.rs` and its `mod codex_stub;` declaration — slice 2's mock-Client integration tests cover what the stub previously enabled, and a silent-success stub on unknown harness names is a footgun. The wildcard arm changes to dispatch a small `UnknownHarness { name }` placeholder whose `run()` immediately returns `Err(Error::UnknownHarness(name))`, preserving the `Box<dyn Harness>` return signature so callers don't change.

### `symphony-core::policy::translate_codex_permissions` (~30 LOC, additive)

```rust
pub(crate) fn translate_codex_permissions(p: &Policy) -> v2::Permissions {
    match (&p.permission_mode, &p.sandbox) {
        (PermissionMode::ReadOnly, _)                                  => Permissions::read_only(),
        (PermissionMode::RequireApproval, _)                           => Permissions::strict(),
        (PermissionMode::AcceptEdits, SandboxProfile::ReadOnly)        => Permissions::read_only(),
        (PermissionMode::AcceptEdits, SandboxProfile::WorkspaceWrite)  => Permissions::workspace_write(),
        (PermissionMode::AcceptEdits, SandboxProfile::Unrestricted)    => Permissions::danger_full_access(),
    }
}
```

Concrete `Permissions` struct shape comes out of typify in stage 1; constructors filled in stage 3.

### Workspace `Cargo.toml`

Add `crates/codex-client` to `members`. Add workspace dev/build deps for `typify` (build-only), keep `tokio`/`serde`/`serde_json`/`thiserror`/`futures` as existing workspace deps.

## Data Flow

### Turn lifecycle

```
Orchestrator        CodexHarness                  codex app-server (child)
─────────────       ─────────────                ──────────────────────
claim_issue ───► run() ─┐
                        │ 1. mcp_bridge::generate_mcp_config_json
                        │ 2. spawn `codex app-server --listen stdio` -c ...
                        │ 3. Client::connect(child) → (client, notif_stream)
                        │ 4. client.initialize(...) ──────────────────────►
                        │   ◄───────────────────────── InitializeResponse
                        │ 5. translate_codex_permissions(policy)
                        │ 6. client.start_turn({prompt, permissions}) ────►
                        │   ◄───────────────────────── TurnStartResponse{turnId}
                        │ 7. AgentEvent::TurnStarted → ctx.tx
                        │
                        │ ── event pump (tokio::select!) ──
                        │   loop {
                        │     notif = stream.next()
                        │     translate_codex_notif(notif)
                        │     → ctx.tx + ctx.bus + (maybe) approval handling
                        │   } until TurnCompleted | transport closed
                        │
                        │ 8. AgentEvent::TurnCompleted/TurnFailed → ctx.tx
                        │ 9. drop(client) → interrupt + kill(child)
                        └► HarnessOutcome { thread_id, turn_id, success, error }
```

### Notification translation

The harness translates ~15 of 63 v2 server notifications. The rest become `AgentEventKind::Notification` with the raw payload preserved for forensics; nothing is broadcast.

| v2 method | `AgentEvent` kind | Bus event | Notes |
|---|---|---|---|
| `turn/started` | `TurnStarted` | `AgentEvent` | turnId stored |
| `turn/completed` | `TurnCompleted` / `TurnFailed` (per status) | `AgentEvent` | terminates pump |
| `turn/diff/updated` | `Notification` | `AgentEvent` | |
| `turn/plan/updated` | `Notification` | `AgentEvent` | |
| `item/started` | — | `ToolCall { tool: "codex.<action>", input }` | |
| `item/completed` | — | `ToolResult { tool, output, error }` | |
| `item/agentMessage/delta` | `OtherMessage` | — | streaming text; **not** broadcast |
| `item/reasoning/textDelta` | — | — | dropped |
| `item/commandExecution/outputDelta` | — | — | dropped (chatty) |
| `item/fileChange/patchUpdated` | `Notification` | `AgentEvent` | |
| `item/autoApprovalReview/started` | — | — | tracked in `pending_reviews` |
| `item/autoApprovalReview/completed` | see below | see below | core approval handling |
| `serverRequest/resolved` | — | — | dropped |
| `thread/tokenUsage/updated` | `TokenUsageUpdated` | `AgentEvent` | |
| `account/rateLimits/updated` | `RateLimitsUpdated` | `AgentEvent` | |
| `error` | `TurnEndedWithError` | `AgentEvent` | |
| `warning` / `guardianWarning` / `deprecationNotice` / `configWarning` | `Notification` | `AgentEvent` | |
| `mcpServer/startupStatus/updated` | `Notification` | `AgentEvent` | useful for diagnosing linear-bridge attach |
| Realtime channels | — | — | unused |
| All others | `Notification` (raw preserved) | — | |

The `tool` field for `ToolCall`/`ToolResult` uses the action discriminator with a `codex.` prefix: `codex.command`, `codex.applyPatch`, `codex.networkAccess`, `codex.mcpToolCall`, `codex.requestPermissions`. Avoids collision with slice-1 bare tool names.

### Approval round-trip (option C — mode-dependent)

On `item/autoApprovalReview/started`: insert `(reviewId → action)` into `pending_reviews`. No event yet.

On `item/autoApprovalReview/completed`, branch on `policy.permission_mode × status`:

| permission_mode | status | Behavior |
|---|---|---|
| `AcceptEdits` | `approved` | `AgentEvent::ApprovalAutoApproved` |
| `AcceptEdits` | `denied` | Emit `OrchestratorEvent::ApprovalRequest { tool: "codex.<action_type>", input: action }`; register `PendingApproval(reviewId)`. Spawn task: await `router.wait(timeout)`; if allow → `client.thread_approve_guardian_denied_action(...)`; if deny → no-op. Emit `ApprovalDecision`. |
| `AcceptEdits` | `timedOut`/`aborted` | `AgentEvent::Notification`; no override |
| `RequireApproval` | `approved` | Treat as `AcceptEdits + approved` (rare given restrictive profile) |
| `RequireApproval` | `denied` | Same as `AcceptEdits + denied` |
| `RequireApproval` | other | As above |
| `ReadOnly` | any | `AgentEvent::Notification`; never override |

`approval_id` for the bus event is the Codex `reviewId`; dashboard correlations use the existing `POST /api/v1/approvals/{id}` with no changes.

`RequireApproval` semantics: every guardian denial reaches operator; auto-approvals are reported but not gated. The mechanism that makes `RequireApproval` work is the restrictive `permissions` profile causing the guardian to deny most actions.

### Policy → `permissions` mapping

| `permission_mode` | `sandbox` | `permissions` on `turn/start` | Override on deny |
|---|---|---|---|
| `AcceptEdits` | `WorkspaceWrite` | workspace-write | yes |
| `AcceptEdits` | `ReadOnly` | read-only | yes |
| `AcceptEdits` | `Unrestricted` | danger-full-access | yes |
| `RequireApproval` | any | most-restrictive | yes (operator gates everything) |
| `ReadOnly` | any | read-only | no |

## Error Handling

### Recovery boundaries

| Error | Fatal? | Why |
|---|---|---|
| Transport EOF mid-turn | fatal (turn) | child died; orchestrator can re-claim |
| Decode error on notification | recoverable | log + `Malformed` event, continue pump |
| Decode error on response | fatal for that RPC | resolve waiter `Err`; if `start_turn`, harness fails |
| JSON-RPC error response | call-site dependent | `start_turn` → fatal; `approveGuardianDeniedAction` → log + skip override |
| Approval timeout | recoverable | router returns deny; same as operator deny |
| `codex` binary missing | fatal (startup) | `StartupFailed` event, failure outcome |

No retries in slice 2. Local stdio doesn't have the transient-failure class retries help with; orchestrator-level re-claim is already supported.

### Cleanup guarantees

`Drop` on `Client`:
1. Best-effort `turn/interrupt` notification (no await, 500ms internal budget).
2. `child.start_kill()`.

`Drop` on `Dispatcher`:
1. Abort the read-loop `JoinHandle`.
2. Drain waiter map — every pending oneshot resolves `Err(TransportClosed)`.

This guarantees: regardless of how `CodexHarness::run` exits (early `?`, panic, normal), the child is killed and no caller hangs.

### Observability

- `tracing::trace` per notification (method + payload), gated by `RUST_LOG=codex_client::dispatcher=trace`.
- `tracing::warn` per error with `error.source()` chain.
- `tracing::Span` per turn carries `issue_id` + `turn_id` for cross-correlation.
- No metrics framework yet; log-only.

### Orchestrator-side handling

`CodexHarness::run` returns `HarnessOutcome { success, error }` — the orchestrator's existing path handles failures uniformly across harnesses. When `success: false`, the post-success VCS hook does not run (consistent with slice 1). Operator decides whether to re-claim.

### Unsupported server notifications

Variants outside the §Data Flow table become `AgentEventKind::Notification` with `raw` populated. No reject path needed — notifications are fire-and-forget by JSON-RPC definition. Unknown methods are surfaced in the trace log for development.

## Testing

### Unit tests (`crates/codex-client/tests/`)

**Protocol round-trip:** For each `ClientRequest`/`ServerNotification` variant we use, `serde_json::from_str` real fixtures from `docs/codex-protocol/v2/*.json`, assert byte-equivalent re-serialization. Catches typify drift and method-name mismatches.

**Transport:** Drive `StdioTransport` against `tokio::io::DuplexStream`:
- Single frame round-trip preserves newline delimiting.
- 3 frames back-to-back yield 3 messages in order.
- Frame split across 2 writes assembles correctly.
- EOF mid-frame → `TransportClosed`, not partial parse.

**Dispatcher:**
- Response with known id → matching oneshot resolves `Ok`.
- Notification → `NotificationStream::next()` yields.
- Malformed JSON line → warn log + continue routing valid frames.
- Unknown response id → log + drop, no panic.
- Drop `Client` → dispatcher exits within 100ms, all pending oneshots resolve `TransportClosed`.

**Client:** Scripted "server" task over `DuplexStream`:
- `initialize` happy path.
- `start_turn` with silent server → caller awaits.
- `start_turn` with error response → caller receives `ClientError::JsonRpc`.
- Drop client mid-`start_turn` → child kill, awaits resolve `Err`.

### Integration tests (`crates/symphony-core/tests/`)

**`CodexHarness` with mocked Client** (no real `codex` binary):
- **Happy path** sequence ending in `turn/completed{success}` → assert `HarnessOutcome { success: true }`, assert `TurnStarted` + `ApprovalAutoApproved` + `TurnCompleted` on `ctx.tx`, assert `ToolCall` + `ToolResult` on `ctx.bus`.
- **Operator override:** sequence ends with `Completed{denied}`. Assert `ApprovalRequest` published. Resolve via `ApprovalRouter::resolve(allow=true)`. Assert mock observed `thread/approveGuardianDeniedAction`. Assert `ApprovalDecision` published.
- **Operator deny:** same, `resolve(allow=false)`. Assert no override RPC.
- **Child crash:** mock drops the notification stream after `TurnStarted`. Assert `HarnessOutcome { success: false, error: Some("transport closed" ..) }`.
- **Policy matrix:** parametrize `(PermissionMode, SandboxProfile)` over all 7 valid combos, assert `translate_codex_permissions` returns the expected variant.

### Deliberately not tested

- Long-running turns (>5min): no regression scenario yet.
- Concurrent turns per client: explicit non-goal.
- `thread/resume` / `fork` / archival: out of scope.
- MCP-bridge connectivity from inside Codex: covered by slice 1's MCP tests; the bridge doesn't care which LLM drives it.
